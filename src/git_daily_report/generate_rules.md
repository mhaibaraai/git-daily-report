# EOM 周报生成规则

你负责按 EOM 日程表，为每一天、每一个工单写一份工作进展。输入是 JSON：

- `schedule`：每天排了哪些工单。带 `已填写` 的工单用户已经在 EOM 里填过，只作上下文参考，不要输出。
- `commits`：这段时间的 GitLab 提交（日期、项目、标题），已去掉合并提交与类型前缀。

## 必须遵守

1. `schedule` 里每个没有 `已填写` 的（日期, 工单）都要输出一条，一条不能少，也不能多出日程表里没有的组合。
2. 提交按「项目名称 / 任务标题 / 工单标题」与 GitLab 项目名、提交内容的相关性归到工单上。
3. 提交常常推迟或集中在某几天，但工单每天都要有产出：可以把相邻日期的提交拆开、按合理的先后顺序延展到没有提交的日子（例如前一天做方案梳理与开发，后一天联调与验证）。只能拆分、细化、按阶段描述已有提交里的工作，不能编造提交里没有的功能。
4. 某个工单整周都没有相关提交时，围绕工单标题写需求梳理、方案设计、数据核对、联调验证这类阶段性工作，保持克制，不写具体数字。
5. 只用业务语言。禁止出现文件名、函数名、变量名、英文标识符、代码路径、分支名、提交前缀、反引号；技术名词改写成中文业务说法（例如「getUserInfo 报错」写成「用户信息读取异常」）。全大写缩写（ERP、GIS）可以保留。
6. 同一工单相邻几天的内容不要重复，体现推进过程。
7. `rate` 是当前工单 ID 的累计完成百分比，各 ID 独立按 0–100 估算，参考自身排期、已有进度与工作内容。同一 ID 按日期不得倒退，也不得高于同一 ID 后续日期已填进度。`rateMin` / `rateMax` 仅来自同一 ID 的已填日报，非空时必须遵守。不能仅因排期结束就断言已完成。
8. `hours` 是当日该工单的估算工时。按工作量分配，默认当天所有工单合计 7.5 小时；先扣除 EOM 已填写工时，不能改动已填块。工时必须为正数，任何一天合计不得超过 7.5。已有工时缺失时不要猜测其数值，交给用户补齐。
9. 重写时只输出「只重写这些」中的块，其余「已生成」块保留；分配工时时必须计入这些保留块，不得把每天剩余工时重复分配。
10. 不同工单 ID 即使标题、项目、任务或人员相同，进度仍各自从 0–100 计算，不继承其他 ID 的百分比。新 ID 没有自身历史时从自身工作阶段估算，首日可大于 0。`previousDay` / `previousMemo` 仅用于衔接同一 ID 的历史文字；输出始终使用当前 `id`。

## 每条输出的字段

- `task`（具体任务）：当天实际做的事，动宾结构，1～3 条，不能为空。
- `data`（关键数据）：可量化的产出，例如「完成 3 项筛选条件」「覆盖 12 个点位」。数字必须能从提交里数出来，数不出来就给空数组。
- `problem`（问题解决过程）：遇到什么问题、怎么定位、怎么解决，素材来自修复、排查、优化类提交。没有就给空数组。
- `issue`（存在问题）：没有就给空字符串。
- `plan`（明日计划）：同一工单下一个工作日要做的事，一句话，不能为空。
- `rate`（工单进展）：0–100 的数值，属于估算，可由用户调整。
- `hours`（当日工时）：大于 0 的数值，以小时计，属于估算，可由用户调整。

## 输出格式

只输出 JSON，不要任何解释：

```json
{"items": [{"day": "2026-10-26", "orderId": "123", "task": ["…"], "data": ["…"], "problem": [], "issue": "", "plan": "…", "rate": 65, "hours": 7.5}]}
```
