# 日报整理规则

这份规则由网页对话与 skills/daily-report 共用，改这里两边同时生效。只讲怎么整理报告，
不含任何通道相关的操作步骤。

## 边界（不可越过）

- 只改措辞与归属，不新增事实。数字、工作项标题、项目名、提交信息一律以报告原值为准。
- 抽不出内容的地方保持为空，如实告诉用户哪几条待补，绝不编造。
- 不改 `id`、`day`、`itemNumber`、`commits`、`confidence`、`candidates` 任何一个字段。
- `generatedTitle` 与 `generatedEntries` 是生成原值，用于识别哪些内容被人改过，不要动。
- 不写 EOM。三段式只是给人复制粘贴的文本，没有任何写回通道。

## 归属存疑的优先处理

`confidence` 不是 `exact` 的工作点是推断出来的，这是整套汇总唯一的准确性风险点，
先处理它们再谈润色：

- `ambiguous` — 同项目下多个工作项都可能，`candidates` 列出了全部候选，问用户该归谁
- `unmatched` — 归不上任何工作项，标题是 GitLab 项目名，问用户对应哪个任务
- `sole` — 项目名对不上，靠「当天只有这一个活跃工作项」兜的底，值得确认一句
- `fuzzy` — 靠标题重合选出的，一般没问题，扫一眼即可

判错的根因通常是项目命名对不上。与其每次手工挪，不如建议用户在
`config/project-mapping.json` 补一条 GitLab 项目名 → Gitee 项目名的覆盖，下次采集就自动对上。

## 工时

EOM 有条硬规则：当天所有工单的实际工时合计不得超过 7.5 小时，超了整批拒收。

用户明确说了才填工时，不要自己估。报告里 `hoursWarning` 非空就是这一天已经超了，
如实提醒用户。

## 明细改写

- 去掉 `feat:` / `fix:` 这类前缀残留和分支名噪音，换成人话。
- 动宾结构，一条明细讲一件事。
- 原始提交把两件事写在一起时可以拆开，但不要合并出原文没有的因果。

## 三段式 memo

段名固定，不可改动，条目之间用全角分号 `；` 连接，每段占一行：

```text
具体任务：…；…
关键数据：…；…
问题解决过程：…；…
```

段标题始终在场——缺内容是缺内容，不是缺段。

- **具体任务** — 当天实际做的事。素材是工作点里未命中问题关键词的那些明细，明细本身
  来自 GitLab 提交标题（合并提交已展开成它带进来的那批）与工作项完成这类节点记录。
- **关键数据** — 可量化的产出，EOM 前端期待「N 条／N 个／从 X 优化至 Y」这类表述。
  提交次数由规则层数出来，不要修改这个数字，只调措辞；数不出来的量化指标不要补。
- **问题解决过程** — 遇到什么问题、怎么定位、怎么解决。素材是命中「修复／定位／排查／
  异常／报错／优化／解决／调整」这类关键词的明细。

## 汇报格式

做完给出：改了几条、哪几条归属仍需用户确认（列出日期与标题）、有多少条明细是空的。
回话简短，不要复述整份报告。
