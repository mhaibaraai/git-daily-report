# EOM 工单流程

本适配器兼容通过企微内页面使用的 `schedule` / `commitReport` 协议，不是企微官方通用工单 API。所有实例地址、填报身份和工时标准由用户配置；脚本不登录企微、不抓取浏览器凭证。

## 拉排期与保存草稿

```bash
python3 /path/to/git-daily-report/scripts/report.py material --config /path/to/settings.local.json --since 2026-01-05 --until 2026-01-09
```

输出包含：

- `path`：草稿文件位置，位于用户工作目录。
- `apply`、`amend`、`revise` 成功保存内容后另返回 `reviewPath`，为自动生成的本地 Markdown 核查稿。
- `material.schedule`：按日期组织的工单、已填内容、草稿和历史进度约束。
- `material.commits`：GitLab 素材；`material.mappings` 为明确配置的工单映射。
- `pending`：需要生成或修正草稿的日期与工单 ID。
- `validation`：当前通过、失败和缺失的块。
- `dailyHours`、`authorFiltered`、`warnings`：工时预算、作者范围及取材限制。

按月读取排期，只认对应月份内的日期，避免日历补位重复。未来日期不填报；工单起始月至今的已填历史用于进度上下界，不扩大提交范围。不同 ID 的同名工单不衔接进度。

刷新不会清空已有草稿。EOM 新增工单会进入待写集合；移除的工单保留为失效项并阻止对应日期提交，避免静默丢失已写内容。素材不足时留空并向用户报告，不编造功能、数字或工作日。

用户明确确认不再填报已移除工单时，可以执行 `material --discard-stale`；失效块转存到报告的 `archivedOrders`，不再参与当前排期校验。不要为绕过错误自动使用此选项。

## 生成输入

将代理撰写的内容保存到临时 JSON 文件：

```json
{
  "items": [{
    "day": "2026-01-06",
    "orderId": "example-order-id",
    "task": ["完善检索条件"],
    "data": [],
    "problem": [],
    "issue": "",
    "plan": "验证检索结果",
    "rate": 40,
    "hours": 4,
    "estimatedFields": ["rate", "hours"],
    "planSuggested": false
  }]
}
```

示例仅展示结构，日期、ID、文字和数字应来自本次素材与用户安排。

- `task`：非空字符串数组，具体工作不能为“无”；`data` 和 `problem` 为字符串数组，可为空，无事实时渲染为“无”。`issue` 无事实时同样填“无”。业务正文不得包含素材分配或生成审核说明；脚本在生成校验和提交预检中拦截已知说明，返回所在字段，要求重写，不静默删除。
- `issue`：字符串，可为空；`plan` 为非空字符串。缺乏已确认计划时可先提出建议，但必须设 `planSuggested: true`，在用户确认前阻止提交。
- `rate`：0–100 的有限 JSON 数值；`hours`：大于 0 的有限数值。拒绝布尔值、数字字符串与非有限数。
- `estimatedFields`：只允许 `rate`、`hours`，省略时默认两者均为估算；只有用户明确提供事实值时才移除对应标记。
- 同一天先扣除 EOM 已填工时，再按工作量估算分配剩余预算；合计不能超过 `daily_hours`。已填工时缺失时不能自行猜补。
- 同一 ID 的百分比不得按日期倒退，也不得越过已填的前后历史进度；不同 ID 独立估算。

执行 `apply <文件.json>` 后读取 JSON 中的 `passed`、`failures`、`missing`。输入日期与 ID 必须来自当前排期，不接受重复或未知键；局部更新会重新校验整天和跨日进度，其他块保持。

## 修正已有百分比

用户明确要求时使用 `amend <文件.json>`，输入为：

```json
{"items": [{"day": "2026-01-06", "orderId": "example-order-id", "rate": 50}]}
```

只允许指定日期、工单 ID 和目标百分比。返回 `changes` 中的原值与目标值供核对；没有提交授权时仅保存提案。文字和工时保持 EOM 当前内容，不根据排期自动线性推到 100%。

提交前如果原百分比或日报 ID 改变，该日阻止提交；重新读取并提出修正后才能继续。目标值与 EOM 当前值相同会撤销该条提案。

## 修正已有正文

使用 `revise <文件.json>` 保存正文修正提案；只支持工单模式：

```json
{"items": [{"day": "2026-01-06", "orderId": "example-order-id", "task": ["集成检索条件展示"], "data": [], "problem": [], "issue": "无", "plan": "核对检索结果"}]}
```

每项必须提供以上七个字段，不接受百分比、工时或其他字段。计划须为用户已确认的安排。命令读取最新排期，仅接受已存在日报；将完整原值快照与目标正文一同保存，`changes` 返回修改前后值供审阅。目标与当前原值相同则清除该项正文修正提案。

刷新和预检保留未生效的正文修正；原日报 ID、正文、百分比或工时任一改变时阻止覆盖，需要重新读取并提出修正。不要与同一记录的百分比修正混用；重新提出一种修正会替换该记录原提案。

保存后用 `show` / `export` 展示实际目标正文。用户确认具体替换稿并明确要求提交后才运行 `submit`；`submit --dry-run` 只预检。更新使用原日报 ID 与 `op=8`，保持最新基线的百分比和工时，提交后核对完整正文及受保护值。日志复用原提交保护，结果未知或冲突时不自动重发。

## 提交前核查与年度归档

每次提交前执行 `report.py review`（保持同一配置、模式、日期、时区），向用户提供返回 `path` 的可点击 Markdown 链接，方便核查。该命令只读取本地报告并保存文档，无需服务凭证。已核查的正文未变化且用户已经授权提交时，不重复请求同一确认；内容变化则先展示新版本。

归档默认位于配置文件旁的 `reports/YYYY/<scope>/`，可用 `archive_dir` 配置固定根目录。文件名为 `<mode>_<since>_<until>_<内容摘要>.md`，按起始年归档。不同正文保留各版本，相同正文复用文件；文件标示报告范围，不将核查稿视为已提交记录，实际提交结果以返回的逐日状态为准。归档仅包含报告正文和本地审核提示，不包含配置、令牌或请求头。

`apply`、`amend`、`revise` 保存内容后自动归档。实际 `submit` 读取最新排期、合并提案后，在任何远程写入前再次归档，并返回 `reviewPath`；归档失败或原文档与内容摘要不一致时停止，不写入 EOM。`submit --dry-run` 保持只读预检，不创建归档，也不改报告或提交日志；核查文档请先用 `review` 生成。用户可保留整个目录用于年度总结，勿把其中所有版本当作独立工作重复统计。

## 提交与回读

- `submit --dry-run`：读取最新排期并预检，不改报告或提交日志。
- `submit`：按天提交；已填日报跳过，只有修正提案使用覆盖操作。
- `submit --retry-unknown`：仅在用户明确要求主动重试时使用，先回读核实，并只在原批次完全未写入且草稿一致时重发。

脚本从最新排期白名单提取提交元数据，不让代理构造部门、人员、项目等接口字段。新增日报使用 `op=4`，百分比及正文修正使用 `op=8` 并携带原日报 ID。两者均使用 `buttonId=increase`、`condition.op=commitReport`，请求携带当日 `reportDate` 和 `otherMatters: []`，单批不混用多个日期。

写入前持久化意图，写请求只发一次；收到成功也必须回读。超时、断线、无法识别的响应或进程中断后，后续运行先核实既有批次。发生内容冲突、部分写入或结果未知时暂停后续日期，不自动重发。

每个日期返回 `submitted`、`skipped`、`ready`、`blocked`、`failed`、`unknown` 或 `conflict`。存在未解决日期时退出码非零；不要把部分成功描述为整段成功。

所有相同实例与填报身份的报告应共享同一配置工作目录。提交日志损坏时停止提交并要求核对，不把损坏当作空记录。不同日期范围共享提交锁，报告编辑有独立锁；状态原子保存。不要删除待核实记录来绕过保护。

## 查看与导出

`show` 返回已有报告 JSON，`export` 返回 `{"markdown": "..."}`；加 `--output <文件.md>` 时另存 Markdown。两者只需非敏感配置，不需要 GitLab 或 EOM 令牌。

GitLab 普通报告模式用 `{"markdown": "..."}` 作为 `apply` 输入，不接受 EOM 提交或百分比修正操作。
