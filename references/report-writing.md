# 报告写作

## 事实边界

提交记录只能证明代码历史中的变更，不能单独证明工作时长、上线状态、验收结果或业务收益。用户提供的工作背景可以补充代码之外的工作；与 Git 信息冲突时指出差异，不自行补全。

- 将相关提交归并成一项可理解的工作，避免把提交数量等同于任务数量。
- 功能、范围、数字和结果都需要依据。提交写“提升性能”，没有测量数据时不能改写成具体提升比例。
- 不把测试代码的新增写成测试执行成功，不把发布配置的修改写成已发布。
- 回滚过的功能不直接写“完成”；结合后续提交说明当前状态，信息不足时保持中性。
- 提交时间用于取材与分组，不承诺那一天完成了全部相关工作。不把一条提交自动铺到多个无提交日期。
- 普通报告不凭修改行数、提交次数或时间跨度推算工时和完成百分比。EOM 模式允许根据工作阶段和配置预算给出明确标注的估算；估算不代表实际测量，也不能改动 EOM 已填值。
- EOM 的关键数据、问题解决过程、存在问题缺少直接事实时填写“无”；“无”表示本次没有填报内容，不扩写为已验证没有问题。普通 Markdown 报告可省略无素材的栏目。
- 下一步计划来自用户或明确的待办事实；用户要求建议时单独标注，不能把建议写成承诺。
- 面向外部的报告按要求匿名化项目、客户和内部标识；不把提交正文整段照搬。

## 默认格式

用户有模板时遵循用户模板。否则使用简短 Markdown：

```markdown
# 工作日报 / 工作周报

时间范围：YYYY-MM-DD 至 YYYY-MM-DD

## 主要进展

- 围绕同一功能归并后的工作内容与有证据支持的结果。

## 问题与后续

- 仅列有事实依据的问题或计划；没有素材时省略本节。
```

多仓库按项目或主题组织；用户需要逐日记录时按实际有素材的日期分组。周报优先总结本周成果和未完成事项，避免堆叠五份日报。

默认用用户使用的语言。面向业务读者解释功能用途；面向技术读者可保留必要术语，不机械删除所有英文或代码标识。

## 交付核对

- 每条成果都能对应提交事实或用户补充。
- 筛选了作者才描述为个人贡献；否则使用仓库或团队进展的表述。
- 已处理重复提交、回滚及后续修复，未夸大完成状态。
- 数字有事实依据；EOM 工时和百分比估算已标注，计划中的建议未伪装为已确认安排。
- 空记录、浅克隆或截断等影响结论的限制已说明。

## EOM 业务正文与本地审核说明

- `task`、`data`、`problem`、`issue`、`plan` 只填写业务工作、数据、处理过程、业务阻碍和已确认计划。
- 素材日期、主题分配、证据缺口、估算依据和生成过程只放在本地审核说明或对话中，不进入 EOM 正文。不要写“按用户要求分配”“非实际提交日期或实测工时”“实际工作日期、投入与完成进度待核实”等说明。
- “关键数据”填写有依据的业务数据或指标；没有则填写“无”，不能改填素材来源。“存在问题”填写真实业务阻碍；缺少提交证据不能直接推断为业务未实施。
- 保留真实的业务待确认事项和技术评估估算。清理生成说明不意味着补写完成、验收、上线或测试通过，也不把集成工作改写为独立开发。
- 最终审阅必须展示将发送的实际正文；本地审核备注与正文分开展示。保存提案不代表获得覆盖已填记录的授权。
